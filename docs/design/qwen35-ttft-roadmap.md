# Qwen3.5-35B-A3B-FP8 TTFT Roadmap (GB10 / Atlas overnight profile)

Generated by the `/loop` TTFT-optimization task on 2026-04-17. Proxy for
Qwen3.6 (same GDN + full-attention + MoE architecture). Numbers measured
on `atlas-gb10:overnight2` at commit `911bcc1`.

Decode baseline: **36.85 tps** @ 128-token output, **36.82 tps** @ 512-token output.

### Gap to theoretical peak

For the 283-token prefill:
- LPDDR5X memory ceiling (273 GB/s, ~35 GB total FP8 weights): **≈128 ms**.
- GB10 FP8 compute peak (~100 TFLOPs, 2 × 283 × 35B active × 40 layers ≈ 1.7 TFLOPs):
  **≈17 ms**.
- Measured: **2349 ms** → 14–18× above the tighter ceiling.

## Bottleneck analysis

### 1. MoE FFN at small N (biggest — 77% of total TTFT)

`moe_fp8_grouped_gemm` launches a grid of `(ceil(N_out/64), max_m_tiles, num_experts)`
CTAs with compile-time `M_TILE=64`.

For N=283, top_k=8, num_experts=256: ~9 tokens per expert on average.
`max_m_tiles = ceil((9 × 2 + 63) / 64) = 1`. Each CTA loads M_TILE=64 rows
of A but only ~9 are live tokens — **≈14% tensor-core utilization on A-tile
rows**. Wasted loads and MMAs.

Further, the E4M3 dequant path uses `__device__ __constant__ float E4M3_LUT[256]`
(lookup table) instead of the hardware `cvt.e4m3x2.rn.satfinite` conversion
available on sm_121. Estimated 2× dequant throughput left on the table.

### 2. Small-N W8A16 GEMM (q_proj / o_proj)

`w8a16_gemm_t` with `M_TILE=64, N_TILE=128` at N=283:
- Grid: `(ceil(N_out/128), ceil(283/64), 1) = (64, 5, 1)` = **320 CTAs**.
- 320 × 128 threads = 40K threads on a ~400K-thread GPU → **10% occupancy**.

q_proj (N=283, K=2048, N_out=8192): 9.5 GFLOPs compute in 7.7 ms = **1.2 TFLOPs**.
GB10 FP8 peak is ~100 TFLOPs → **~1% of peak**.

### 3. No CUDA graph capture for prefill

`model.rs` captures CUDA graphs for decode (fixed shape). Prefill reruns
every kernel eagerly. At 600+ kernel launches per forward pass, at ~5 µs
each = 3 ms of pure launch overhead — small but not zero. More importantly,
it blocks the driver's ability to schedule micro-ops optimally.

## Prioritized fixes (effort × impact)

### P0 — New `moe_fp8_grouped_gemm_small_m` variant

- **Effort**: ~1 full engineering day. New CUDA file with `M_TILE=16`
  (or `M_TILE=8`, or per-expert dynamic dispatch via templates).
- **Impact**: if we regain the 14% → 80% utilization gap, **MoE FFN
  drops from 46 ms → ~8 ms**. Across 40 layers, that's **~1500 ms saved**
  = TTFT from 2349 ms → ~850 ms. **2.8× speedup.**
- **Risk**: new kernel, needs parity tests against existing path.
- **Dispatch rule**: when `avg_tokens_per_expert < 32`, call small-M
  variant; else call current M_TILE=64. Avg crosses 32 at N ≈ 1024 for
  256 experts, top_k=8 — so the small-M path dominates at the agentic
  prompt lengths users hit.

### P1 — Hardware FP8 cvt in grouped GEMM

- **Effort**: 2–4 hours. Replace `E4M3_LUT_GMOE[byte]` with inline PTX
  `cvt.rn.e4m3x2.f32` (or bf16 variant).
- **Impact**: ~1.5–2× dequant throughput → **MoE FFN 46 ms → 28–35 ms**.
  Stacks with P0.
- **Risk**: SM version check; add `#if __CUDA_ARCH__ >= 1210` guard.

### P2 — Fused `moe_fp8_grouped_gate_up`

- **Effort**: ~1 day. Analogous to the existing `moe_expert_gate_up_shared_fp8`
  but for routed experts.
- **Impact**: saves one pass over the activation tensor and one kernel
  launch per layer. Small — maybe 10–15% on MoE phase. ~5 ms saved
  across 40 layers.

### P3 — CUDA graph capture for a fixed prefill chunk size

- **Effort**: 1–2 days. Capture a graph once per (chunk_len, batch) combo,
  cache and replay. Tricky because chunk_len varies; bucket to the
  nearest power of 2 or nearest 128.
- **Impact**: 3–5 ms of launch overhead per forward pass. Small at these
  scales but guaranteed.

### P4 — Tune `w8a16_gemm_t` for small M

- **Effort**: 4–8 hours. M_TILE=16 or M_TILE=32 variant; dispatch by M.
- **Impact**: q_proj 7.7 ms → maybe 2–3 ms. ×10 attention layers = **~50 ms**.
  Modest on the grand total.

## Expected TTFT if all of P0+P1+P2 land

| Prompt tokens | Baseline | After P0+P1+P2 | Target (10%) |
|---|---|---|---|
| 283 | 2349 ms | ≈ 800 ms (2.9×) | 235 ms |
| 1101 | 4225 ms | ≈ 1800 ms (2.3×) | 423 ms |
| 4372 | 11848 ms | ≈ 8000 ms (1.5×) | 1185 ms |

**Closing to 10× requires deeper work**: quantize activations to FP8 (so
the GEMM does FP8×FP8 instead of BF16×FP8), cp.async staging for MoE
weights, possibly a persistent-kernel MoE dispatch that keeps experts
resident across layers. Each of those is 1–2 weeks of engineering.

## Decode-TPS guard

All changes above must pass `bench/qwen36_ttft.py --baseline
bench/qwen36_ttft_overnight2-baseline.json` which fails on >3% decode
regression from 36.82 tps. The MoE grouped-GEMM path is shared between
prefill and decode — P0 is the highest regression risk; hence the guard.
