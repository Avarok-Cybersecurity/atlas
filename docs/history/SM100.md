# Atlas on NVIDIA B200 (SM100) — Porting Roadmap

**Target**: 8x NVIDIA B200 (SM100, 192GB HBM3e, 160 SMs, NVLink 5)
**Source**: NVIDIA GB10 (SM121, 120GB LPDDR5X, 48 SMs)
**Primary model**: DeepSeek V3 (671B, MLA + 256 experts top-8 + MTP)

---

## Hardware Delta

| | GB10 (SM121) | B200 (SM100) |
|---|---|---|
| Compute Capability | 12.1 | 10.0 |
| SMs | 48 | 160 |
| Memory | 120 GB LPDDR5X, 273 GB/s | 192 GB HBM3e, ~8,000 GB/s |
| Tensor Cores | 4th gen (BF16 m16n8k16, FP8 m16n8k32) | 5th gen (FP4 m16n8k32, FP6, FP8, BF16) |
| Native E2M1 MMA | No (software dequant to BF16) | Yes (`mma.sync.m16n8k32.f32.fp4.fp4.f32`) |
| ldmatrix.x4 | Broken (manual uint32 workaround) | Likely fixed |
| ldmatrix.trans | Broken (manual transpose) | Likely fixed |
| Multi-CTA Clusters | Forced 1x1x1 | Configurable (up to 16 CTAs) |
| Tensor Memory (TMEM) | No | Yes (register-like, dedicated to tensor ops) |
| NVLink | None (single-chip superchip) | NVLink 5, 900 GB/s bidirectional per pair |
| L2 Cache | Unknown (<48 MB) | 96 MB |

**Key insight**: SM100 is NOT a minor revision of SM121. Different PTX ISA, different tensor core instructions, different memory hierarchy. A naive recompile with `-arch=sm_100` will run but leave most of the hardware capability unused.

## What Works As-Is (no changes needed)

### Rust model code (~90% reusable)
- **MLA (Multi-head Latent Attention)**: Full implementation from Mistral Small 4 — latent projections, absorbed attention, compressed KV cache. DeepSeek V3 MLA is architecturally identical.
- **MoE routing**: Parametric `num_experts` (tested up to 256), `num_experts_per_tok` (tested up to 10), shared expert with sigmoid gating. DeepSeek V3 uses 256 experts top-8 + 1 shared — fits existing config.
- **MTP (Multi-Token Prediction)**: K=2 speculative decoding head, fully implemented.
- **NVFP4/FP8 weight loading**: Compressed-tensors format, per-group scales. Format is hardware-independent.
- **Paged KV cache**: Variable head dimensions, block-based allocation. Layout is hardware-independent.
- **Config parsing, weight loading, scheduling, API server**: Pure Rust, no GPU dependency.

### Simple CUDA kernels (element-wise, recompile only)
- `rms_norm.cu` — reduction kernel, no MMA
- `rope.cu` — position encoding, scalar math
- `reshape_and_cache.cu` — memory copy/reshape
- `moe_topk.cu`, `moe_permute.cu` — sorting/routing, integer ops
- `embedding.cu` — table lookup
- `ssm_preprocess.cu` — exponential/clamp, scalar
- `ssm_state_norm.cu` — reduction

These kernels use no SM-specific instructions and will work on SM100 after recompilation.

## What Must Be Rewritten

### Tier 1: Critical Hotpath (45%+ of decode time)

#### W4A16 GEMM (`w4a16_gemm.cu`, `w4a16_gemm_t.cu`, all model-specific overrides)

**Current**: Dequant E2M1 nibbles → BF16 via LUT → MMA `m16n8k16.f32.bf16.bf16.f32`
**SM100**: Native FP4 MMA `m16n8k32.f32.fp4.fp4.f32` — skip dequant, 2x throughput

This is the single most impactful rewrite. Every decode token reads ~1.5 GB of weights through this kernel.

Changes needed:
- New MMA path: load packed E2M1 directly, apply FP8 block scales, feed to FP4 tensor core
- Remove E2M1_LUT constant memory lookup (native conversion)
- Re-tune M_TILE/N_TILE for 160 SMs (current 64x64 may underutilize)
- Consider persistent kernel variant (grid-stride loop over tiles)

**Effort**: 3-5 days
**Impact**: ~2x decode throughput improvement

#### Inferspark Prefill (`inferspark_prefill.cu`, `inferspark_prefill_v47.cu`)

**Current**: Tiled online softmax with cp.async + MMA m16n8k16. Contains two SM121-specific workarounds:
- Line ~222: Manual Q register loading (ldmatrix.x4 broken on SM121)
- Line ~231: Manual K transpose (ldmatrix.trans broken on SM121)

Changes needed:
- Test ldmatrix.x4 and ldmatrix.trans on SM100; if fixed, revert to native loads (5-10% speedup)
- Re-tune BR (row tile) for 160 SMs — current BR=32 may leave SMs idle when num_heads < 160
- Evaluate CTA clustering for shared L1 across attention heads

**Effort**: 2-3 days
**Impact**: 10-20% prefill speedup

### Tier 2: Significant Optimization

#### Dense GEMM TC (`dense_gemm_tc.cu`)

Same ldmatrix.x4 workaround as Inferspark. Remove manual uint32 loads from shared memory, use native ldmatrix if SM100 supports it.

**Effort**: 1 day

#### E2M1 Quantization (`quantize_bf16_to_nvfp4.cu`, `e2m1_branchless.cu`)

Current software E4M3 conversion (bit manipulation fallback). SM100 may support native `cvt.rn.satfinite.e4m3x2.f32` PTX instruction.

**Effort**: 1 day
**Impact**: Faster online quantization for KV cache

#### MoE Grouped GEMM (`moe_w4a16_grouped_gemm.cu`)

Inherits W4A16 improvements. Once W4A16 is rewritten with FP4 MMA, the MoE dispatch path gets the same benefit.

**Effort**: Automatic (follows W4A16 rewrite)

### Tier 3: Performance Tuning (works but suboptimal)

All remaining kernels work on SM100 but assume 48 SMs and 273 GB/s bandwidth:

- **Paged decode attention** (`paged_decode_attn_nvfp4.cu`): Memory-bound, benefits from 8 TB/s but may need wider coalescing
- **SSM kernels** (`gated_delta_rule.cu`, `mamba2_ssm_decode.cu`): Register-heavy, may benefit from TMEM
- **MoE blend/permute**: Works but grid sizing assumes 48 SMs

**Effort**: 1-2 days each, profile-driven

## What Must Be Built New

### Tensor Parallelism (TP=8) — THE BLOCKER

Atlas currently has Expert Parallelism (EP=2) only. DeepSeek V3 at 671B requires TP=8:

- 671B x 0.5 bytes (NVFP4) = 336 GB — needs at least 2 GPUs
- With KV cache + activations: TP=8 across 8x B200 (192 GB each) is the target

**What TP requires**:
1. **Weight sharding**: Split Q/K/V/O projections and FFN weights across TP ranks at load time
2. **All-gather / reduce-scatter**: After each parallel GEMM, synchronize activations via NCCL
3. **TP-aware buffer allocation**: Each rank allocates 1/TP of weight memory, full activation memory
4. **Combined TP+EP dispatch**: MoE experts split by EP, attention/FFN split by TP
5. **CUDA graph compatibility**: Graph capture with NCCL sync points (may require NCCL 2.20+ features)

**Existing infrastructure to build on**:
- `spark-comm/src/nccl_backend.rs`: NCCL 2.29.7 bindings with all-reduce, all-gather, reduce-scatter, send/recv
- `spark-model/src/layers/ep_dispatch.rs`: Expert dispatch across ranks (extend from EP=2 to EP=N)
- `spark-server/src/main.rs`: Multi-rank launch via environment variables (EP_RANK, EP_WORLD_SIZE)

**Effort**: 6-8 weeks (largest single item)

### B200 Build Target

Create `/workspace/atlas/kernels/b200/HARDWARE.toml`:

**Effort**: 1 day

### DeepSeek V3 Weight Loader

Add `deepseek_v3` model type to `factory.rs` and implement weight loader in `weight_loader/deepseek_v3.rs`. Architecture is MLA + MoE + MTP — all components exist, just need config mapping and weight name translation.

**Effort**: 3-5 days

## Phased Rollout

### Phase 1: Naive Port (1-2 weeks)
- Create B200 build target (HARDWARE.toml, build.rs)
- Copy all SM121 kernels, recompile with `-arch=sm_100`
- Validate correctness on B200 hardware
- **Expected perf**: ~30-50% of B200 peak (running BF16 MMA on FP4-capable hardware)

### Phase 2: Core Kernel Rewrites (2-3 weeks)
- W4A16 GEMM with native FP4 MMA
- Remove ldmatrix workarounds (test first on real hardware)
- Re-tune tile sizes and grid dimensions for 160 SMs
- **Expected perf**: ~70-80% of B200 peak

### Phase 3: Tensor Parallelism (6-8 weeks)
- TP core infrastructure (weight sharding, NCCL sync)
- Extend EP from EP=2 to EP=N
- Combined TP+EP for DeepSeek V3
- **Unlocks**: 671B model on 8x B200

### Phase 4: SM100 Optimization (2-3 weeks)
- TMEM integration for register-heavy kernels (SSM, attention accumulators)
- CTA clustering for MoE dispatch and attention
- Persistent kernels for full 160-SM utilization
- Profile-driven tile size search
- **Expected perf**: ~90-95% of B200 peak

## Critical Unknowns (need real hardware to resolve)

1. **ldmatrix.x4 / ldmatrix.trans on SM100** — broken on SM121, workarounds baked into 3+ kernels. Need to test on B200 before removing workarounds.

2. **Native E2M1 PTX instructions** — `cvt.rn.satfinite.e2m1x2.f32` missing on SM121. SM100 5th-gen tensor cores advertise FP4 support but the conversion PTX may still require software path.

3. **TMEM availability and programming model** — SM100 docs mention tensor memory but CUDA toolkit support may lag. Check CUDA 13.x release notes.

4. **CTA clustering performance** — theoretical benefit for MoE dispatch (group expert CTAs), but may increase register pressure. Need microbenchmarks.

5. **L2 cache behavior with NVFP4** — 96 MB L2 on SM100 may cache weight tiles that currently spill to DRAM. Could change optimal tile sizes significantly.

6. **NCCL performance on NVLink 5** — need to verify ring vs tree topology selection and measure actual all-reduce latency for TP sync points.
