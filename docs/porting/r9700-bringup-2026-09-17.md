# Atlas on gfx1201 (Radeon AI PRO R9700): the 2026-09-17 bring-up run

The ledger of the first night on RDNA 4 silicon, written by the autonomous driver that ran it and lightly path-scrubbed (`$WORK` is the test box's work root). It is a record, not a recipe: the recipe is `build-amd.sh` / `serve-amd.sh` with `ATLAS_TARGET_HW=r9700` and the r9700 section of `docs/HARDWARE.md`.

One line: **Atlas now builds, serves and generates correct text on an AMD RDNA4
board, for both target models.** Ornith-1.0-9B at NVFP4 runs at 78 to 80 tok/s
decode with a clean 30 minute soak, 530 requests, zero errors and not one byte of
VRAM growth; **Qwen3.8-27B, the primary target, came up on the last rung of the
night at 30.9 tok/s** once the loader learned to release consumed tensors and the
transposed prefill twins were turned off. The night found and fixed seven
distinct defects on the way there, two of them in SCALE rather than in Atlas.

Driver: autonomous session, tracks T0, T1, T2, and then T3 onward under a
sequence of orchestrator instructions. Every remote command went through the
`rl` audit wrapper; the trail is on the box in
`$WORK/audit/tom-2026-09-1{6,7}.log` and locally in

## The five defects, in the order they were hit

Each was isolated with a probe that does not involve Atlas, so the boundary
between "Atlas bug" and "SCALE bug" is measured rather than argued.

### 1. SCALE over-reports memory use (SCALE defect)

Every early serve died in an OOM guard reading 0.05 GB free while sysfs showed
9 GB free. Two standalone probes, one built with SCALE's nvcc and one with
hipcc, allocating in a loop and printing the runtime's number next to the
kernel's:

* 512 MiB chunks: both runtimes agree with sysfs. SCALE at 28672 MiB allocated
  reports 3704 MiB free, HIP 3884 MiB.
* 11 MiB chunks, the granularity of a 1953-tensor shard: **SCALE's free memory
  reaches 4 MiB after only 9900 MiB is allocated**, with sysfs confirming 10571
  MiB in use and about 21 GB genuinely free. It charges about 44 MiB per 11 MiB
  request, a factor of 4, and does not recover it on free (32376 -> 64 -> 22064
  MiB). **HIP in the same test stays accurate and recovers fully.**

So the defect is SCALE's runtime accounting for many small allocations, not ROCm
or HSA. Fixed on the branch by taking free VRAM from amdgpu sysfs on SCALE
builds; the serve log now prints `free-memory source: amdgpu sysfs
/sys/class/drm/card1/device` and, at debug level, all three legs side by side:
`cuMemGetInfo=0.027 GiB, sysfs=9.358 GiB, MemAvailable=115.998 GiB`.

### 2. The r9700 kernel set was a stale subset (Atlas)

With truthful memory the load completed and then failed on `Module
'dense_gemv_bf16_batch2' not loaded`. `kernels/r9700/common` carried 93 `.cu`
against `kernels/gb10/common`'s 179. Fixed by mirroring the whole gb10 set minus
what gfx1201 cannot compile.

### 3. The mirror included a file gfx1201 cannot compile (Atlas)

Build 4 then failed on `w4a16_fp8_ldmab.cu`, which my T2b superset census had
already listed in the e4m3 group hours earlier. **The census predicted the build
failure exactly.** Fixed by dropping it as expected-absent.

### 4. SCALE hands back a phantom function handle (SCALE defect)

Next failure was `CUDA_ERROR_INVALID_IMAGE (200)` on the first launch, with no
kernel name anywhere: the launch site in `crates/atlas-core/src/registry.rs:457`
formats its error from the launch config and the name is not in scope. Four
probes settled what was and was not broken:

| Probe | Result |
|---|---|
| P1 vector add, runtime API | **OK.** SCALE kernels do run on this board |
| P2 driver API + `cuModuleLoadData` of a `--cuda-device-only -c` relocatable, Atlas's exact path | **OK**, every call CUDA_SUCCESS |
| P3e object with an undefined `__device__` symbol | launch returns **302**, not 200, ruling that mechanism out |
| P6 sweep of all 176 objects and 580 symbols through load, getfunc and `cuFuncGetAttribute` | every object loads, every kernel resolves; one object, `t0__nvfp4_mmq.o`, has **no kernel symbols at all** |

An `LD_PRELOAD` interposer over `cuModuleGetFunction` and `cuLaunchKernel`,
which needs no source change, then named the culprit in one line:

```
LAUNCH FAIL kernel=atlas_nvfp4_repack grid=[5440,1,1] block=[256,1,1] smem=0 rc=200
```

And the C1 probe isolated the driver behaviour behind it:

```
cuModuleLoadData    -> 0 (CUDA_SUCCESS)
cuModuleGetFunction -> 0 (CUDA_SUCCESS)   handle=0x63247949d300     <-- for a symbol that is not there
cuFuncGetAttribute  -> 200 (CUDA_ERROR_INVALID_IMAGE)
cuLaunchKernel      -> 200 (CUDA_ERROR_INVALID_IMAGE)
```

NVIDIA's driver returns `CUDA_ERROR_NOT_FOUND` at the lookup. SCALE returns
success and a phantom handle, so the error surfaces later and in the wrong
place. Why the module is empty: all 13 `__global__` bodies in
`kernels/gb10/qwen3.6-27b/nvfp4/nvfp4_mmq.cu`, including `atlas_nvfp4_repack` at
line 142, sit inside `#if defined(BLACKWELL_MMA_AVAILABLE)`. Fixed on the branch
by having the registry read the ELF symbol table instead of trusting the driver,
and by declaring `nvfp4_mmq` expected-absent for this target.

### 5. The SSM prefill asked for a kernel this arch cannot have (Atlas)

With the guard in place the server came up and every request still failed at
layer 0:

```
Inference error: prefill_chunk failed: Prefill chunk layer 0 failed: ssm prefill:
out_proj GEMM failed: Kernel lookup w4a16_fp8_ldmab::fp8_fp8_gemm_ldmab:
Module load failed: Module 'w4a16_fp8_ldmab' not loaded
```

That is the file dropped in defect 3, so the dispatch had no fallback. Fixed by
not building an FP8 predequant when no kernel can read it. **After that fix the
server serves, unprompted, with no override flags.**

### 6 and 7. The loader held every tensor, and leaked some (Atlas)

With the 9B serving, the 27B still died at layer 28 of 64. The fix was two
commits: release each checkpoint tensor the moment a loader consumes it, and a
lever for the transposed second weight layout. The same load then reported
**19.42 GB resident against 33.73 GB of demand**, including "3.36 GB of dequant
intermediates freed that the pre-release loader leaked" and two double frees
fixed alongside. That, plus a smaller inference reserve at batch 1, is what put
the 27B on the board.

## The shim bisect, two live variables and a third that is not

The plan names three shims. On this branch only one of them has a reader:
`ATLAS_W4A16_VARIANT` (`crates/spark-model/src/layers/mod.rs`).
`ATLAS_FORCE_GLOBAL_GDN` and `ATLAS_NO_FP8_PREDEQUANT` had **no readers** in the
Rust tree at the start of the night; the second live knob is
`ATLAS_NO_GDN_FP8_PREFILL`
(`crates/spark-model/src/weight_loader/qwen35_dense.rs`). Exporting the dead ones
changes nothing, so the bisect has two real variables, not three.

| Config | Started | A | B | C (391?) | tok/s (server) | First error |
|---|---|---|---|---|---|---|
| a, baseline (`W4A16=v1`, `NO_GDN_FP8_PREFILL=1`) | yes | coherent | coherent | yes | 78.1 to 78.7 | - |
| b, `NO_GDN_FP8_PREFILL` unset | yes | fails | fails | n/a | - | `kernel lookup w4a16_fp8_ldmab::fp8_fp8_gemm_ldmab at crates/spark-runtime/src/op_cache.rs:70 failed AFTER the boot audit sealed` |
| c, `W4A16_VARIANT` unset | yes | coherent | coherent | yes | 78.4 to 78.9 | - |
| d, `--kv-cache-dtype fp8` | yes | coherent | coherent | yes | **37.9 to 38.0** | - |

Readings. (b) says `ATLAS_NO_GDN_FP8_PREFILL=1` is **required** on this card,
because without it the QKVZ GEMM asks for the e4m3 kernel that cannot compile
here. (c) is **not a real A/B**: `w4a16_gemm_v2` is absent on gfx1201, so the
dispatch lands on v1 whatever the environment says, which is why the numbers
match the baseline. (d) is coherent but **halves decode**, so bf16 KV stays the
recommendation on this board even though MODEL.toml prefers fp8. The recommended
configuration is (a).

### Qwen3.8-27B: it fits now, and the last two commits are why

Earlier in the night the 27B died at layer 28 of 64 with the sweep reading

```
2631 allocation(s) totalling 33.73 GB had no owner; largest sites:
  crates/spark-runtime/src/fast_weights/mod.rs:434      (22332.5 MB x1968)
  crates/spark-model/src/weight_map/quantized.rs:261    (5202.5 MB x157)
```

The 22.3 GB store stayed resident while the model build layered transposed and
requantized copies on top, peaking at 34110529536 B on a 31.9 GB board. Two
changes closed it: releasing each checkpoint tensor the moment a loader consumes
it, and a lever to skip the transposed prefill twins. Rung N then reported

```
weights resident: store 14.06 GB (9.35 GB released on consume across 232 tensors),
layer-owned 5.36 GB, total 19.42 GB; 3.36 GB of dequant intermediates freed that
the pre-release loader leaked
transposed prefill twins: skipped (ATLAS_LOAD_TRANSPOSED_TWINS=0),
projected 12.74 GiB (ffn 8.96 + ssm 2.90 + attn 0.88), prefill fast arms off
```

33.73 GB of demand became 19.42 GB resident. Rung N was still refused, but by the
KV sizer rather than an allocator: `budget 25.5 GB, but 23.0 GB already consumed +
6.0 GB inference reserve = 29.0 GB committed`. Rung N2 at util 0.90 and batch 1
shrank the inference reserve from 6.0 GB to 2053 MB and the SSM ring to 1.18 GB,
and the server came up:

```
KV cache: 31.9 GB total x 90% util = 28.7 GB budget; 23.0 GB pre-KV + 2.0 GB
reserve -> 3.7 GB for KV -> 258 blocks x 16 tok/block = 4128 max KV tokens
```

**Results on the 27B.** Coherent on all three prompts; prompt A returned "A KV
cache is a memory optimization technique that stores the computed Key and Value
vectors from previous attention layers to avoid redundant calculations during
autoregressive token generation"; the canary returned **391**; the oracle set
wrote **40 records with 0 errors and 0 empty outputs**. Decode **30.9 tok/s** by
the server's counter (26.82 tok/s wall median of 3 x 250 tokens), TTFT 1.21 s on a
short prompt. Prefill: 2263 prompt tokens at **TTFT 26.82 s, about 84 tok/s**, and
the reply correctly described the input. VRAM steady 29223047168 B of
34208743424 B.

**The caveats are real and should not be lost.** This arm runs with the
transposed prefill twins OFF, which the log itself warns costs FFN prefill
throughput (about 7 TFLOP/s against about 51 for `w4a16_gemm_t_m128` on the
Gemma-4-31B measurement), and it serves at batch 1 with 4128 KV tokens, which is
a single short conversation and no more. It also runs at utilization 0.90 on a
board whose desktop is live. It is a bring-up result, not a serving
configuration. For context only, gfx1151 Strix Halo did about 8.8 tok/s decode on
a 27B; this is a different checkpoint on a discrete board, so do not read 30.9
against 8.8 as a speedup.

The checkpoint composition is worth carrying forward: the NVFP4 repo is **mixed**,
23.4 GB on disk of which only 7.49 GB is 4-bit packed MLP, 10.6 GB is FP8
(attention, linear_attn, lm_head) and 4.37 GB is BF16 (embeddings). The FP8 repos
are 29 GB on disk, including the supposed qwen3.6 fallback, so they are heavier,
not lighter.

## vLLM, the reference that never was

Six attempts, two images. Docker reaches the card correctly: the image A smoke
printed `vllm 0.28.0`, `torch 2.11.0+gitd0c8b1f`, device 0 `gfx1201` 34.2 GB and
device 1 `gfx1036` (the iGPU), and every container pinned `HIP_VISIBLE_DEVICES=0`.

| # | Image | Checkpoint | mml | util | Outcome |
|---|---|---|---|---|---|
| 1 | A | Qwen3.8-27B-FP8 | 16384 | 0.75 | weight-load OOM, 112 MiB free, 28.99 GiB held |
| 2 | A | Qwen3.8-27B-FP8 | 4096 | 0.75 | identical, so context is not the variable |
| 3-5 | A | Qwen3.8-27B-NVFP4 | 16384, 8192, 4096 | 0.75 | weights resident, then a byte-identical OOM in profiling: 784 MiB requested, 30.53 GiB held |
| 6 | A | Qwen3.8-27B-FP8 | 2048 | 0.93 + `--enforce-eager --max-num-seqs 2` | identical weight-load OOM |

Image B was pulled but not run: 28.75 GiB of weights against a 31.86 GiB board
with a desktop on it is arithmetic no image changes. Two notes for the next
driver: image A has `ENTRYPOINT null`, so the documented `serve ...` argv must be
`vllm serve ...`; and 30.53 GiB held under `--gpu-memory-utilization 0.75` means
**that build does not treat the flag as a hard cap**. Consequence: no
`t1-oracle-vllm.jsonl` and no `t1-vllm-rest.json`, so the cross-engine half of
T5 and T8 is `SKIP (no reference server)`. As the plan says, vLLM is a reference
and not ground truth; nothing here is evidence about Atlas's correctness.
